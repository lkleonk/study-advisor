FU Berlin CS Consultant Agent Flow

Backend-only LangGraph flow. Course offerings use exact JSON bucket lookup; pure degree-rule questions go directly to the answer node, and study-plan validation is owned by deterministic Python code. Every session is bound to one degree program (degree_id seeded into the checkpoint at creation); each node resolves its prompts, parse schema, and validator from the degree registry in backend/app/domain/degrees/. The LLM never chooses the degree.

Lookup scope: active course-offering lookup reads the session degree's projection of backend/app/domain/data/course_offerings/<semester>.json through keys like sose26/technical/swp. Degrees without tagged offerings get an honest "no local course-offering data" note without an LLM selector call. degree_question messages skip lookup and are answered from reference context rendered from the degree's program_rules.py. The classifier sees two user turns but not the full rule catalogue; it enables the large cross-university-courses section only for HU/TU cross-registration questions and related follow-ups. Individual course URLs stay in source data but are omitted from lookup answer context and URL citations by default; deployments can enable them with AGENT_COURSE_LOOKUP_INCLUDE_COURSE_URLS=true. The plan_check path exists only for degrees with plan_validation_enabled (currently msc_informatik); for other degrees ScopeClassifier downgrades it to degree_question. It runs parser, deterministic rule checker, then AnswerComposer; parser schema and validator come from the degree package (msc_informatik, msc_data_science). For a chat follow-up, the parser receives the existing plan JSON plus the latest user message and returns one complete updated plan before validation. For msc_informatik, validation separates 70 LP Informatik, 10 LP Anwendungsbereich, 10 LP Wahlbereich, and the 30 LP thesis. Wahlbereich credits do not satisfy subject or specialization minima and do not raise the whole-plan caps of 2 Softwareprojekte and 4 seminars. Nullable counted_in_bachelor and used_for_master_admission fields distinguish module level from prior credit use; confirmed reuse is an error, while missing Bachelor-level credit history produces a warning. The always-included checklist-planning reference lists canonical module slots and LP. The composer checks dedicated named modules before broad topic slots and considers desired future courses to preserve flexible slots. This advice remains available when the detailed HU/TU section is excluded; external module recognition still requires a Prüfungsausschuss decision.
Error handling: the classifier, course-key selector, and study-plan parser use local heuristics when their LLM calls fail. If AnswerComposer cannot produce a valid, non-empty answer, SessionService returns HTTP 502 with answer_generation_failed; no fallback answer is returned.
WizardFlow 0.9.0 tracing: workflow and node context managers capture execution timing and finalize requests, including failures. Enabled requests receive an SDK-generated workflow ID stored as wizardflow_message_id; per-request opt-out uses no-op scopes and writes no trace data. LLM nodes record exact llm_input payloads containing prompt and msg, plus llm_output or llm_error; deterministic nodes record input and output. Only executed application nodes are recorded; synthetic __start__ and __end__ markers are omitted. Transcript text is unredacted. JSONL traces are written under backend/traces/ and excluded from Git.
